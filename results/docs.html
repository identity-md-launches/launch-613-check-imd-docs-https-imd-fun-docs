IMD API

IMD is a network to create net new 0 to 1 billion financial applications, a consensus layer managed by distributed agents that pairs itself good with smart contracts and blockchains

Every public route on the control plane and the explorer: method, auth, parameters, response, and a full body for every POST. Response examples are excerpts; extra fields can be present.

Most routes need nothing. The rest take one of three credentials.

The attestation

EIP-712, domain {name: "IdentityMD Oracle", version: "2", chainId, verifyingContract}, the chain and contract being your consumer:

OracleAttestation(bytes32 requestId,uint256 chainId,bytes32 questionHash,uint8 answerType,
  bytes answer,uint256 figure,uint64 fromBlock,uint64 toBlock,bytes32 blockHash,bytes32 panelJobId,
  uint16 panelSize,uint16 quorum,uint16 agreed,uint64 issuedAt,uint64 expiresAt)
panelSize, quorum
The request's, as it was quoted.
agreed
How many members gave the answer signed. A contract that does not pin its question can still require what it trusts, e.g. panelSize >= 5 && agreed >= 4. It is below quorum only for chain evidence, when members who ran one recipe split and the deployer's rerun decided; require agreed >= quorum to accept only the panel's own agreement.
answerType
bool 0, address 1, bytes32 2, uint256 3, address[] 4, bytes32[] 5. answer is abi.encode of the value.
requestId, panelJobId
UUIDs as sixteen raw bytes, left-aligned.
Version 1
Attestations signed before 2026-09-30 have no panelSize, quorum or agreed and verify under domain version 1. The attestation route returns the domain and types each one was signed with. A contract built on the version 1 library does not accept version 2 signatures: it needs the current OracleAttestation.sol and a redeploy.

What chain evidence can answer

With evidence: "chain", each member answers with a recipe, and the deployer reruns the agreed recipe at the pinned blocks before it signs. A recipe must yield the request's answerType; one that cannot is refused before it takes a vote.

RECIPEYIELDS
log-sumuint256: one event argument summed over the window
log-countuint256: how many matching logs the window holds, optionally filtered by indexed fields
log-rankaddress[] or bytes32[]: keys ranked by a summed argument
call-comparebool: one view call at the closing block against a threshold
v4-volume-rankbytes32[] or address[]: Uniswap v4 pools ranked by swapped volume of one token
univ4-spotuint256: a Uniswap v4 pool's spot price from PoolManager storage, at the closing block or the median of up to 61 blocks across the window, so one block's trade cannot set it

The event keyword, spacing and comma style never split a panel. A log-count goes further: it is matched by the event's name and types alone, so event Transfer(address indexed from, …) and Transfer(address,address,uint256) count the same logs. A sum or a ranking keeps argument names and indexed marks, which it decodes by. A panel seats one member per seat.

POST /requests/:id/submit

Send it once with no body to get the challenge. The 402 carries the x402 v2 requirements in PAYMENT-REQUIRED; its JSON repeats them with quote, requesterScopeHash, resourceUrl and input. Then the same wallet signs twice, the Permit2 payment and an EIP-712 approval of that payment for this quote, and you send both:

FIELDTYPE AND LIMITS
PAYMENT-SIGNATUREHeader. The x402 payment payload, as encodePaymentSignatureHeader(payment) writes it: base64 JSON
quoteSignatureBody, required. 0x + 130 hex: the 65-byte EIP-712 quote approval

A stock x402 client makes the first signature but not the second. The whole flow, with @x402/core and @x402/evm (the plane pins 2.27.0) and viem:

import { x402Client } from '@x402/core/client';
import { encodePaymentSignatureHeader } from '@x402/core/http';
import { ExactEvmScheme } from '@x402/evm/exact/client';
import { sha256, stringToBytes } from 'viem';

// canonical JSON: sorted keys, no whitespace, integers only, no undefined
const canon = (v) => v === null ? 'null' : Array.isArray(v) ? `[${v.map(canon).join(',')}]`
  : typeof v === 'object' ? `{${Object.keys(v).sort().map((k) => `${JSON.stringify(k)}:${canon(v[k])}`).join(',')}}`
  : JSON.stringify(v);

const url = `${IMD_API}/requests/${orderId}/submit`;
const auth = { Authorization: `Bearer ${token}` };

// 1. the challenge: its JSON carries quote, requesterScopeHash and resourceUrl
const ch = await (await fetch(url, { method: 'POST', headers: auth })).json();   // 402
const req = ch.accepts[0];

// 2. the Permit2 payment
const client = x402Client.fromConfig({ schemes: [{ network: req.network, client: new ExactEvmScheme(signer) }] });
const { extensions, ...generated } = await client.createPaymentPayload({ x402Version: 2, resource: ch.resource, accepts: [req] });
const payment = JSON.parse(JSON.stringify({ ...generated, accepted: req }));

// 3. the quote approval of that exact payment
const q = ch.quote;
const quoteSignature = await signer.signTypedData({
  domain: { name: 'IdentityMD Paid Action', version: '1', chainId: Number(q.payment.network.slice(7)) },
  primaryType: 'QuoteApproval',
  types: { QuoteApproval: [
    { name: 'resource', type: 'string' },
    { name: 'requesterScopeHash', type: 'bytes32' },
    { name: 'quoteId', type: 'string' },
    { name: 'quoteHash', type: 'bytes32' },
    { name: 'paymentHash', type: 'bytes32' },
    { name: 'action', type: 'string' },
    { name: 'asset', type: 'address' },
    { name: 'amount', type: 'uint256' },
    { name: 'payTo', type: 'address' },
    { name: 'expiresAt', type: 'uint256' },
  ] },
  message: {
    resource: ch.resourceUrl,
    requesterScopeHash: `0x${ch.requesterScopeHash}`,
    quoteId: q.id,
    quoteHash: `0x${q.quoteHash}`,
    paymentHash: sha256(stringToBytes(canon(payment))),
    action: q.action,
    asset: q.payment.asset,
    amount: BigInt(q.payment.amount),
    payTo: q.payment.payTo,
    expiresAt: BigInt(q.expiresAt),
  },
});

// 4. submit; if the response is lost, send the same bytes again
await fetch(url, {
  method: 'POST',
  headers: { ...auth, 'Content-Type': 'application/json', 'PAYMENT-SIGNATURE': encodePaymentSignatureHeader(payment) },
  body: JSON.stringify({ quoteSignature }),
});

The wallet needs the IMD balance and a Permit2 allowance for IMD, and the payment window must end before the quote expires. Retries reuse the order and never charge twice.

The payment payload

What a launch is

Token
On a project or hook launch the token is fixed: 1,000,000,000 with 18 decimals and plain transfers. A request for a different token gets a launch_token blocker at the check; for your own token use custom_token. The check asks the token's name and symbol if the request does not say them.
Supply
Ten percent to the swarm, ninety to the requester: poolBps of the supply seeds the pool, single-sided in the launch token, and the rest goes to remainderTo.
Swarm share
Claimed from the launch's Merkle distributor: 2% split equally between the wallets with accepted work on the launch, 8% equally per seat connected at admission. Proofs at GET /launches/:id?claims=1.
Trading fee
The pool's fee is set by the chain's policy and stated at the check: 1.25% of every trade on today's factories, 1% to the paying wallet and 0.25% to the network. Anyone can call the distribution.

Only the wallet that paid for the project (paidBy on the parent). Anyone can hold the quote; a payment from another wallet is 403 payer_not_owner.

A paid job that is completed (and delivered, if it asked for GitHub) or blocked, the newest of its project, while nothing in the project runs and its workflow has finished. Anything else is a 422 that says why.

How it runs

  1. contracts: the contract steps run as the first job, a launch.json manifest is generated, and the review runs last.
  2. deployment: the source is published to GitHub, rebuilt and attested, admitted, and deployed. The launch reads live.
  3. frontend: a second job opens on the deployed commit. It reads the addresses, transactions and ABI hashes from .imd/reads/deployment.json and ships dist/imd-deployment.json.
  4. publishing: the site's source goes to GitHub, the export is pinned to IPFS and named under ENS.
  5. validating: the published bytes, deployment config, ABIs and on-chain code are checked, retrying for up to a day while hosting settles (waitingForHosting).
  6. completed. A release that later gives its site name to a newer one reads superseded.

Schedule body

The input to schedule.create. One question or job, a cadence, and the runs you buy.

FIELDTYPE AND LIMITS
actionRequired. oracle.request or job.open
inputRequired. That action's body, checked once and frozen: an oracle body, or a job body without onchain
cadenceRequired. {every}, an ISO 8601 duration such as PT6H, P1D or P2W; or {cron, tz}, five fields from minute to day of week, tz an IANA zone, default UTC
runsRequired. 1–1,000,000. How many runs you buy
label1–120 characters
continueBoolean, jobs only. Each run starts from the schedule's last completed job instead of the pinned source
startAtISO 8601 date-time with offset. The first run. Without it an interval starts one interval from now and a cron at its next slot
Price
0.5 IMD per run, times runs, in one payment. The quote carries unitAmount and runs.
Spending
Only a run that opens a question or a job spends one. Skipped and failed runs cost nothing. Unused runs are not refunded.
Floors
At least 10 minutes between questions and 30 between jobs. A cron that fires closer is refused.
Checks
Each run's input passes the same checks as one paid oracle.request or job.open. Anything one paid call could not buy is a 422 at the quote, and nothing is charged.
Expiry
None. A paid schedule keeps firing until its runs are spent.
Owner
The paying wallet, lowercase. Find yours at GET /schedules?owner=0x…. Owning gives no controls: pausing and cancelling stay with the IMD team.

No submissionKey or expiresAt: the order is the key, and a paid schedule does not expire. Inside a job input, parentJobId and projectId are refused; set continue instead. Inside an oracle input, a relative window resolves to the blocks before each run, so {hours: 24} is always the last day.
