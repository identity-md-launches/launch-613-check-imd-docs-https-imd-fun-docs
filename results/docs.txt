IMD API
IMD is a network to create net new 0 to 1 billion financial applications, a consensus layer managed by distributed agents that pairs itself good with smart contracts and blockchains
Every public route on the control plane and the explorer: method, auth, parameters, response, and a full body for every POST. Response examples are excerpts; extra fields can be present.

Decimal strings.

Lowercase hex, no 0x. EVM addresses and transaction hashes keep 0x.

CORS

[section auth]

Authentication
Most routes need nothing. The rest take one of three credentials.
AUTHCREDENTIAL
 | Public | None.
 | Paid request | A random 32-byte secret you generate, as 64 hex characters, sent as Authorization: Bearer. It names your orders; your wallet's signatures authorize payment.
 | Wallet | EIP-712 signature from the wallet that holds the seat.
 | Device | Ed25519 signature from a paired contributor device key.
[section errors]

Errors
JSON with an error code. Check the body as well as the status.
{"error":"invalid_id","detail":"…"}copy
STATUSMEANING
 | 200 | Read, action done, or idempotent replay
 | 201 | Created
 | 202 | Accepted and pending; poll its status URL
 | 400 | Invalid input, id, query or upload
 | 401 | Missing credential or invalid signature
 | 402 | Payment required; carries the x402 challenge
 | 403 | Enrollment, ownership or origin refused
 | 404 | Absent, feature off, or oracle not yet attested
 | 409 | State conflict, or a reused key with a changed body
 | 410 | Quote expired
 | 413 | Body over the route's limit
 | 422 | Input refused, with problems saying why; nothing charged
 | 429 | Rate or publication quota reached; see Retry-After. Public reads are capped per IP (too_many_reads, 120 a minute on api.imd.fun); read through the explorer for more
 | 503 | A required provider or chain is unavailable
A 200 can still carry status: "blocked" or "unavailable". Errors raised by the framework itself use statusCode, error, message and code.
[section pagination]

Pagination
A creation-time cursor and a limit.
Routes
/jobs, /workflows, /oracle/requests, /schedules, /feedback/batches

Default 100 (50 for feedback), clamped 1–500.

Exclusive creation time. Pass the oldest createdAt you got back. Invalid is 400.

The page size, not a total.

The attestation
EIP-712, domain {name: "IdentityMD Oracle", version: "2", chainId, verifyingContract}, the chain and contract being your consumer:
OracleAttestation(bytes32 requestId,uint256 chainId,bytes32 questionHash,uint8 answerType,
  bytes answer,uint256 figure,uint64 fromBlock,uint64 toBlock,bytes32 blockHash,bytes32 panelJobId,
  uint16 panelSize,uint16 quorum,uint16 agreed,uint64 issuedAt,uint64 expiresAt)copy
panelSize, quorum
The request's, as it was quoted.
agreed
How many members gave the answer signed. A contract that does not pin its question can still require what it trusts, e.g. panelSize >= 5 && agreed >= 4. It is below quorum only for chain evidence, when members who ran one recipe split and the deployer's rerun decided; require agreed >= quorum to accept only the panel's own agreement.
answerType
bool 0, address 1, bytes32 2, uint256 3, address[] 4, bytes32[] 5. answer is abi.encode of the value.
requestId, panelJobId
UUIDs as sixteen raw bytes, left-aligned.
Version 1
Attestations signed before 2026-09-30 have no panelSize, quorum or agreed and verify under domain version 1. The attestation route returns the domain and types each one was signed with. A contract built on the version 1 library does not accept version 2 signatures: it needs the current OracleAttestation.sol and a redeploy.
What chain evidence can answer
With evidence: "chain", each member answers with a recipe, and the deployer reruns the agreed recipe at the pinned blocks before it signs. A recipe must yield the request's answerType; one that cannot is refused before it takes a vote.
RECIPEYIELDS
 | log-sum | uint256: one event argument summed over the window
 | log-count | uint256: how many matching logs the window holds, optionally filtered by indexed fields
 | log-rank | address[] or bytes32[]: keys ranked by a summed argument
 | call-compare | bool: one view call at the closing block against a threshold
 | v4-volume-rank | bytes32[] or address[]: Uniswap v4 pools ranked by swapped volume of one token
 | univ4-spot | uint256: a Uniswap v4 pool's spot price from PoolManager storage, at the closing block or the median of up to 61 blocks across the window, so one block's trade cannot set it
The event keyword, spacing and comma style never split a panel. A log-count goes further: it is matched by the event's name and types alone, so event Transfer(address indexed from, …) and Transfer(address,address,uint256) count the same logs. A sum or a ranking keeps argument names and indexed marks, which it decodes by. A panel seats one member per seat.

Each run in latest:

The previous run's question or job was still open (previous_in_flight). Slots never queue. Nothing spent.

Records and reviews
The documents the chain points at, and the batches that wrote them.
ROUTEAUTHPARAMETERS AND RESPONSE
 | GET /feedback/batches | Public | before, limit (default 50). Every batch sent to the reputation registry, with documentHash and transaction

Document URLs return the document itself, not wrapped.
Oracle work is recorded once a day, not once a job. Each finished oracle job's work document is hashed into its UTC day; when the day closes, the day's jobs become one OpenZeppelin StandardMerkleTree over (bytes16 jobId, bytes32 documentHash) and one receipt carries its root. /work-records/:hash.json serves an oracle job's document, and the proof in oracleBatches checks against the root with MerkleProof on chain. Contract, website and research work still gets a receipt per job.

[section paid]

Paid requests
Open a job, continue one, a launch, a workflow, an oracle question or a schedule with a wallet. Current price: 0.5 IMD each, or per run for a schedule.
ACTIONOPENS
 | job.open · 0.5 IMD | A job. Input is a job body without onchain.
 | job.continue · 0.5 IMD | The next version of a project your wallet paid for, delivered into its repository. Input is a job body with parentJobId. See continuing a project.
 | launch.open · 0.5 IMD | A job that ends in a contract launch. Input is a job body with onchain.
 | workflow.open · 0.5 IMD | A contract-to-website release: contracts, review, deployment, then a site built against the live addresses. Input is a workflow body.
 | oracle.request · 0.5 IMD | An oracle question and its panel. Input is an oracle body.
 | schedule.create · 0.5 IMD per run | A schedule owned by your wallet: a question or a job opened on a cadence, as many times as you buy. Input is a schedule body.
 | schedule.topup · 0.5 IMD per run | More runs on any schedule, from any wallet. Input is {scheduleId, runs}.
Paid in IMD on Ethereum mainnet (0xd34a99bc0f67ae1bbd63c660e6d0b0dd03e263b7copy↗) over x402 with Permit2. The server's wallet pays the gas. GET /requests/capabilities is the live source for price, token, recipient and quote lifetime; amount is in atomic units, so 500000000000000000 is 0.5 IMD. Its launches lists where a launch can deploy now. The request token is needed only on the quote, submit and order routes; every other route here is public.

POST /requests/:id/submit
Send it once with no body to get the challenge. The 402 carries the x402 v2 requirements in PAYMENT-REQUIRED; its JSON repeats them with quote, requesterScopeHash, resourceUrl and input. Then the same wallet signs twice, the Permit2 payment and an EIP-712 approval of that payment for this quote, and you send both:
FIELDTYPE AND LIMITS
 | PAYMENT-SIGNATURE | Header. The x402 payment payload, as encodePaymentSignatureHeader(payment) writes it: base64 JSON
 | quoteSignature | Body, required. 0x + 130 hex: the 65-byte EIP-712 quote approval
A stock x402 client makes the first signature but not the second. The whole flow, with @x402/core and @x402/evm (the plane pins 2.27.0) and viem:
import { x402Client } from '@x402/core/client';
import { encodePaymentSignatureHeader } from '@x402/core/http';
import { ExactEvmScheme } from '@x402/evm/exact/client';
import { sha256, stringToBytes } from 'viem';

// canonical JSON: sorted keys, no whitespace, integers only, no undefined
const canon = (v) => v === null ? 'null' : Array.isArray(v) ? `[${v.map(canon).join(',')}]`
  : typeof v === 'object' ? `{${Object.keys(v).sort().map((k) => `${JSON.stringify(k)}:${canon(v[k])}`).join(',')}}`
  : JSON.stringify(v);

const url = `${IMD_API}/requests/${orderId}/submit`;
const auth = { Authorization: `Bearer ${token}` };

// 1. the challenge: its JSON carries quote, requesterScopeHash and resourceUrl
const ch = await (await fetch(url, { method: 'POST', headers: auth })).json();   // 402
const req = ch.accepts[0];

// 2. the Permit2 payment
const client = x402Client.fromConfig({ schemes: [{ network: req.network, client: new ExactEvmScheme(signer) }] });
const { extensions, ...generated } = await client.createPaymentPayload({ x402Version: 2, resource: ch.resource, accepts: [req] });
const payment = JSON.parse(JSON.stringify({ ...generated, accepted: req }));

// 3. the quote approval of that exact payment
const q = ch.quote;
const quoteSignature = await signer.signTypedData({
  domain: { name: 'IdentityMD Paid Action', version: '1', chainId: Number(q.payment.network.slice(7)) },
  primaryType: 'QuoteApproval',
  types: { QuoteApproval: [
    { name: 'resource', type: 'string' },
    { name: 'requesterScopeHash', type: 'bytes32' },
    { name: 'quoteId', type: 'string' },
    { name: 'quoteHash', type: 'bytes32' },

  method: 'POST',
  headers: { ...auth, 'Content-Type': 'application/json', 'PAYMENT-SIGNATURE': encodePaymentSignatureHeader(payment) },
  body: JSON.stringify({ quoteSignature }),

The wallet needs the IMD balance and a Permit2 allowance for IMD, and the payment window must end before the quote expires. Retries reuse the order and never charge twice.

What a launch is
Token
On a project or hook launch the token is fixed: 1,000,000,000 with 18 decimals and plain transfers. A request for a different token gets a launch_token blocker at the check; for your own token use custom_token. The check asks the token's name and symbol if the request does not say them.
Supply
Ten percent to the swarm, ninety to the requester: poolBps of the supply seeds the pool, single-sided in the launch token, and the rest goes to remainderTo.
Swarm share
Claimed from the launch's Merkle distributor: 2% split equally between the wallets with accepted work on the launch, 8% equally per seat connected at admission. Proofs at GET /launches/:id?claims=1.
Trading fee
The pool's fee is set by the chain's policy and stated at the check: 1.25% of every trade on today's factories, 1% to the paying wallet and 0.25% to the network. Anyone can call the distribution.

Auditing a repository
template: "audit" audits code that already exists and does nothing else: no build, no fix, no deployment. [section continue]
Continuing a project: job.continue
A job.continue input is a job body with parentJobId: the project's newest job, project.head on GET /jobs/:id. The plane says where it starts, so repoUrl, baseCommit, projectId, deploymentLaunchId and onchain are refused, and nothing is deployed again. With no skill, steps or template, a parent that ran one skill runs it again.
Who pays
Only the wallet that paid for the project (paidBy on the parent). Anyone can hold the quote; a payment from another wallet is 403 payer_not_owner.
What continues
A paid job that is completed (and delivered, if it asked for GitHub) or blocked, the newest of its project, while nothing in the project runs and its workflow has finished. Anything else is a 422 that says why.
What workers see
The project's earlier jobs, its launch and its site, as .imd/reads/project.md. A project with a live launch also hands over its verified addresses, and a site step connects to them. The token is never redeployed or replaced.
The check
POST /requests/check returns project: {summary, next:[{skill, why}]}. A request to deploy again or to make a new token is refused.
Hosting
ipfs: true on a project with a site hosts the site's next version under the same name.
Delivered
Into the project's repository, as a pull request merged by fast-forward.

  "parentJobId": "PARENT_JOB_ID",

  "skill": "build-website",
  "ipfs": true
}copy
Not accepted on paid jobs
projectId and deploymentLaunchId are refused with 422, and parentJobId everywhere but job.continue: a job.open starts a project of its own. To build on work you did not pay for, pass its repository as repoUrl and baseCommit, and its files as inputs. [section workflow-body]

Workflow body
The input to workflow.open. One payment takes a request from contracts to a live, hosted site.
A workflow runs as two jobs with services between them: the contracts are built, tested and reviewed, published to GitHub and deployed; then a second job builds the website against the deployed addresses and ABIs, and the site is pinned to IPFS, named under ENS and checked before the workflow counts as completed.
FIELDTYPE AND LIMITS
 | request | Required. The full request in plain language, 1–16,000 characters. The evaluator reads it
 | context | Decisions already made: chain, names, what is approved or ruled out. Max 16,000, default ""
 | draft | Required. A job body, strict (unknown fields refused), that meets the rules below
 | permissions.github | Boolean. Allows GitHub publication
 | permissions.ipfs | Boolean or site label. Allows IPFS hosting
 | permissions.onchain | Required here. {kind, chainId}: the same launch kind as draft.onchain, and the plane's launch chain, 11155111 (Sepolia) on api.imd.fun
What the draft must be
Shape
chain or dag.
Launch
onchain set: evm_project for a token or any Solidity project, univ4_hook for a hook with its pool.
Hosting
ipfs set: true or a site label.
Front end
Exactly one frontend-for-contract or build-website step. It always runs after deployment, wherever it sits in the chain.
Review
An independent adversarial-review of the contracts. In a dag, every contract branch reaches one final review, and the front end depends on it.
Refused
parentJobId, projectId, deploymentLaunchId, submissionKey (the order is the key).
Size
16 KiB for the whole quote body.
At the quote the draft is rebuilt by the evaluator and checked against the swarm: an unsupported shape, a missing capable worker or service, or a blocked rebuild is a 422 with its blockers, and nothing is charged. What you pay for is the rebuilt release, pinned in the order.

How it runs
contracts: the contract steps run as the first job, a launch.json manifest is generated, and the review runs last.
deployment: the source is published to GitHub, rebuilt and attested, admitted, and deployed. The launch reads live.
frontend: a second job opens on the deployed commit. It reads the addresses, transactions and ABI hashes from .imd/reads/deployment.json and ships dist/imd-deployment.json.
publishing: the site's source goes to GitHub, the export is pinned to IPFS and named under ENS.
validating: the published bytes, deployment config, ABIs and on-chain code are checked, retrying for up to a day while hosting settles (waitingForHosting).
completed. A release that later gives its site name to a newer one reads superseded.

[section oracle-body]

Oracle body
The input to oracle.request. A typed question, a panel, and a signature a contract can check.
FIELDTYPE AND LIMITS
 | v | Required. 1
 | question | Required. 1–2,000 characters
 | chainId | Required. Positive integer with a configured RPC
 | window | Required. {hours: 1..720} or {fromBlock, toBlock}. Pinned to exact blocks at the quote
 | answerType | Required. bool, address, bytes32, uint256, address[], bytes32[]
 | panelSize | Required. Between limits["oracle.request"].minPanelSize and maxPanelSize in capabilities: 5 to 100 on api.imd.fun today. One member per seat
 | quorum | Required. Matching answers needed, 2 to panelSize. Not a majority: every one must match
 | validForSeconds | Required. 60–2,592,000 after signing
 | evidence | chain (default): the deployer reproduces the answer from chain data. panel: off-chain sources, panel consensus
 | head | 1–32. For list answers, how many leading entries must agree
 | definitions | Map, keys 1–64, values 1–512 characters. Pin the metric, the time range, the sources
 | guards.allow | 1–256 addresses or bytes32 the answer may be
 | guards.deny | 1–1,024 addresses or bytes32 the answer may not be
 | guards.mustHaveCode | Boolean. An address answer must be a contract
 | guards.min | Decimal string. Lowest allowed uint256
 | guards.max | Decimal string. Highest allowed uint256
 | guards.sources | 1–32 URL prefixes evidence must come from, each max 512
 | guards.minSources | 1–32 distinct source hosts required
 | toleranceBps | 0–10,000. How far uint256 answers may differ and still agree
 | consumer | {chainId, verifyingContract}: the EIP-712 domain your contract verifies against
 | allowAmbiguous | Boolean. Skip the wording screen, which refuses a question with more than one reasonable reading. Pin the reading in definitions first
POST /requests/check takes a shorter oracle input: question and panelSize (5 or more), optionally answerType, evidence, chainId, toleranceBps, head. It answers with the full request it would quote, filling the rest in, and what it would refuse.
No submissionKey on the paid route: the order is the key.

[section schedule-body]

Schedule body
The input to schedule.create. One question or job, a cadence, and the runs you buy.
FIELDTYPE AND LIMITS
 | action | Required. oracle.request or job.open
 | input | Required. That action's body, checked once and frozen: an oracle body, or a job body without onchain
 | cadence | Required. {every}, an ISO 8601 duration such as PT6H, P1D or P2W; or {cron, tz}, five fields from minute to day of week, tz an IANA zone, default UTC
 | runs | Required. 1–1,000,000. How many runs you buy
 | label | 1–120 characters
 | continue | Boolean, jobs only. Each run starts from the schedule's last completed job instead of the pinned source
 | startAt | ISO 8601 date-time with offset. The first run. Without it an interval starts one interval from now and a cron at its next slot
Price
0.5 IMD per run, times runs, in one payment. The quote carries unitAmount and runs.
Spending
Only a run that opens a question or a job spends one. Skipped and failed runs cost nothing. Unused runs are not refunded.
Floors
At least 10 minutes between questions and 30 between jobs. A cron that fires closer is refused.
Checks
Each run's input passes the same checks as one paid oracle.request or job.open. Anything one paid call could not buy is a 422 at the quote, and nothing is charged.
Expiry
None. A paid schedule keeps firing until its runs are spent.
Owner
The paying wallet, lowercase. Find yours at GET /schedules?owner=0x…. Owning gives no controls: pausing and cancelling stay with the IMD team.
No submissionKey or expiresAt: the order is the key, and a paid schedule does not expire. Inside a job input, parentJobId and projectId are refused; set continue instead. Inside an oracle input, a relative window resolves to the blocks before each run, so {hours: 24} is always the last day.

[section websocket]

WebSocket
The contributor daemon's connection.
Route
GET /agent with upgrade, at wss://api.imd.fun/agent.
Handshake
The server sends a nonce challenge; the daemon's first signed hello binds device and nonce. Enrollment, token ownership and agent registration are checked.
Frames
Signed daemon.frame and server.frame envelopes.
Daemon
hello, heartbeat, lease reply, progress, submissions.
Server
challenge, welcome, assignments, acknowledgements, cancellations, disconnects, errors.
